## 1. Definition of Workflow

Для організації роботи використовую Kanban-дошку GitHub Projects. Спочатку створено 12 планових карток F-001–F-012, пов'язаних із лабораторними роботами ЛР3, ЛР5 та ЛР6. Після відкриття другого конверта додано термінову картку F-013.

Мета Kanban — зробити процес виконання завдань прозорим, обмежити кількість одночасної роботи, своєчасно виявляти блокування та вимірювати швидкість проходження карток.

Дошка складається з п'яти колонок.

| Колонка | Умови входу | Умови виходу |
| --- | --- | --- |
| Backlog | Завдання створено, визначено назву, ключ та очікуваний результат. | Уточнено обсяг, критерії завершення та необхідні матеріали. |
| Ready | Завдання зрозуміле, його можна виконати приблизно за 1–2 дні, критичні залежності перевірено. | Виконавець починає роботу, а WIP-ліміт дозволяє взяти нову картку. |
| In progress | Розпочато фактичне виконання, зафіксовано дату початку. | Підготовлено результат, який можна перевірити. |
| Review | Результат доступний у репозиторії та готовий до перевірки. | Результат прийнято й картку переведено в Done або повернуто на доопрацювання. |
| Done | Критерії завершення виконано, результат перевірено, зафіксовано дату завершення. | Картка залишається в Done як підтвердження виконаної роботи. |

Для кожної картки фіксую:

- Унікальний ключ.
- Тип роботи.
- Дату створення.
- Дату початку виконання.
- Дату завершення.
- Кількість календарних днів блокування.
- Посилання на результат (Artifact).
- Cycle time у календарних днях.

**Формула:**

`Cycle time = дата завершення − дата початку роботи`

Якщо завдання почали та завершили одного дня, cycle time дорівнює 0 календарних днів.

До cycle time не включається час перебування в Backlog і Ready до фактичного початку роботи.

## 2. WIP-ліміти

WIP (Work In Progress) — максимальна кількість карток, які можуть одночасно перебувати в певному стані.

| Колонка | Початковий WIP | Поточний WIP | Пояснення |
| --- | :-: | :-: | --- |
| In progress | 3 | 2 | 2026-11-08 ліміт зменшено за першим конвертом. |
| Review | 2 | 2 | Обмежує накопичення неперевірених результатів. |

Для Backlog, Ready та Done робочі WIP-ліміти не встановлено.

### Що роблю, коли ліміт вичерпано

Якщо в In progress уже дві картки, нову роботу не починаю. Спочатку завершую одну з поточних карток і передаю її на перевірку.

Якщо в Review перебувають дві картки, спочатку перевіряю одну з них і переводжу в Done або повертаю на доопрацювання.

Заблокована картка залишається незавершеною. Причину блокування, дату та необхідні дії записую в журнал.

Основне правило: **спочатку завершувати розпочату роботу, а потім брати нову.**

### Коли ліміт спрацював

На початку спостереження випадків очікування через WIP-ліміт не зафіксовано.

Початковий стан після завершення F-001:

| Колонка | Карток |
| --- | :-: |
| Backlog | 11 |
| Ready | 0 |
| In progress | 0 |
| Review | 0 |
| Done | 1 |

2026-11-08 WIP In progress зменшено з 3 до 2.

На момент зміни ліміту колонка In progress була порожньою. Тому зменшення ліміту не спричинило негайного блокування роботи.

Під час подальшого спостереження фіксуватиму фактичні випадки, коли нову картку неможливо взяти через заповнений WIP.

### Метод розрахунку

Для кожної завершеної картки:

`Cycle time = дата завершення − дата початку роботи`

Мінімальний cycle time — найменше значення серед завершених карток.

Максимальний cycle time — найбільше значення серед завершених карток.

Середній cycle time:

`Середній cycle time = сума cycle time / кількість завершених карток`

Незавершені картки до розрахунку не включаються.

### Колонка, де картки чекали найдовше

За поточними скріншотами найбільше незавершених карток накопичено в Backlog.

Однак це не доводить, що саме Backlog є головним вузьким місцем: для такого висновку потрібні фактичні дати переходів і тривалість очікування карток.

Після завершення спостереження проаналізую час проходження Ready, In progress та Review, щоб визначити причини затримок.

У підсумку необхідно записати:

## 7. Рішення ретроспективи з ЛР3

**Перед Sprint Planning перевіряти готовність зовнішніх залежностей і не включати до спринта історії з непідтвердженими критичними умовами.**
