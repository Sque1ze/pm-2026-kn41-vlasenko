## 1. Definition of Workflow

Для організації роботи використовую Kanban-дошку GitHub Projects. На дошці розміщено 12 робочих завдань, пов'язаних із підготовкою документації семестрового проєкту та лабораторними роботами ЛР5 і ЛР6.

Основна мета — контролювати кількість одночасних завдань, своєчасно виявляти блокування та вимірювати фактичний час виконання роботи.

Дошка складається з п'яти колонок.

| Колонка | Картка потрапляє сюди, коли | Картка виходить звідси, коли |
| --- | --- | --- |
| Backlog | Створено завдання з унікальним ключем F-001–F-012, назвою, описом та очікуваним результатом. Завдання ще не підготовлене до виконання. | Уточнено обсяг роботи, визначено критерії завершення та перевірено наявність необхідних матеріалів. |
| Ready | Завдання зрозуміле, має перевірювані критерії завершення та достатньо малий обсяг для виконання за 1–2 дні. | Виконавець фактично починає роботу, а в In progress є вільне місце відповідно до WIP-ліміту. |
| In progress | Розпочато реальну роботу над завданням, зафіксовано дату початку та визначено очікуваний результат. | Підготовлено результат, виконано основні критерії завдання та є файл або посилання для перевірки. |
| Review | Завдання виконано та передано на перевірку. Результат доступний у репозиторії або іншому погодженому місці. | Результат перевірено. Якщо критерії виконані — картка переходить у Done; якщо знайдено недоліки — повертається в In progress. |
| Done | Усі критерії завершення виконано, результат перевірено, посилання на нього доступне, дату завершення записано. | Картка залишається у Done як підтвердження виконаної роботи. |

Картки рухаються між колонками тільки після фактичної зміни стану роботи.

Для кожної картки фіксую:

- Унікальний ключ F-001–F-012.
- Тип роботи.
- Дату створення.
- Дату початку роботи.
- Дату завершення.
- Кількість календарних днів блокування.
- Cycle time у календарних днях.

Для розрахунку часу виконання використовую формулу:

**Cycle time = дата завершення − дата початку роботи.**

Якщо картку розпочато та завершено одного дня, cycle time дорівнює 0.

## 2. WIP-ліміти

WIP (Work In Progress) визначає максимальну кількість карток, які одночасно перебувають у певному стані.

| Колонка | Ліміт | Чому саме такий |
| --- | :-: | --- |
| In progress | 3 | Дозволяє виконувати не більше трьох завдань одночасно. Це зменшує перемикання між задачами та допомагає зосередитися на завершенні розпочатої роботи. |
| Review | 2 | Обмежує кількість неперевірених результатів, щоб перевірка не ставала вузьким місцем потоку. |

Колонки Backlog, Ready та Done не потребують обмеження кількості карток.

**Що я роблю, коли ліміт вичерпано:**

Якщо в In progress уже перебувають три картки, нову роботу не починаю. Спочатку завершую одну з поточних задач, передаю її на перевірку та звільняю місце.

Якщо в Review уже дві картки, спочатку перевіряю та завершую одну з них, а не додаю третю.

Якщо завдання заблоковане зовнішньою залежністю, фіксую причину блокування та намагаюся її усунути. Заблокована картка не вважається завершеною.

Основне правило — **спочатку завершувати розпочате, а не постійно брати нову роботу.**

**Коли ліміт спрацював:**

На момент початкового налаштування дошки випадків очікування через вичерпання WIP-ліміту ще не підтверджено.

Після першого такого випадку буде записано дату, ключ картки, заповнену колонку та дію, яку було виконано замість початку нової роботи.

Після відкриття першого конверта встановлений ліміт In progress потрібно буде змінити відповідно до нової умови й спостерігати за його впливом на потік.

1. Дата створення не дорівнює даті початку роботи.

3. Завершення фіксується тільки після перевірки результату.
4. Дні блокування рахуються лише тоді, коли робота вже почалася, але була зупинена через зовнішню причину.

До відкриття конверта потрібно зафіксувати поточний стан усіх колонок та WIP-лімітів.

**Стан дошки до конверта:**

Очікує завершення п'ятої картки. Потрібно вказати її ключ, дату завершення та розподіл решти завдань між колонками.

**Що зупинили, щоб пропустити термінову картку:**

Буде записано після відкриття другого конверта та прийняття рішення.

Термінова картка має пройти через той самий процес, що й звичайні завдання, але з вищим пріоритетом. Наявні WIP-ліміти при цьому не скасовуються.

**Скільки вона зайняла від появи до завершення:**

Потрібно записати дату появи, дату початку та дату завершення термінового завдання.

Тривалість від появи до завершення обчислюється в календарних днях.

**Що робимо, якщо таких карток стане три на тиждень:**

Якщо термінових завдань стає три на тиждень, це свідчить про системну проблему з плануванням або пріоритетами.

Я пропоную виділити для таких запитів окремий клас обслуговування expedite з обмеженою кількістю одночасних термінових карток.

Кожен терміновий запит повинен мати обґрунтування та підтверджений вплив на дедлайн або результат проєкту.

Якщо нові термінові запити регулярно витісняють планову роботу, переглядаю правила пріоритезації та резерв часу на непередбачені завдання.

## 6. Перший вимір

Перший вимір потоку проводиться після завершення щонайменше восьми карток.

Робоча ціль — завершити всі 12 карток. Якщо за два тижні завершено менше восьми, необхідно окремо пояснити причину. За умовою ЛР4 для здачі такого неповного спостереження потрібно мати щонайменше чотири завершені картки.

| Показник | Значення |
| --- | :-: |
| Найкоротший cycle time, днів | — |
| Найдовший cycle time, днів | — |
| Середній cycle time, днів | — |
| Завершених карток у вимірі | — |

**Метод розрахунку:**

Cycle time кожної завершеної картки визначається як різниця між датою завершення та датою початку роботи.

Найкоротший cycle time — мінімальне значення серед завершених карток.

Найдовший cycle time — максимальне значення серед завершених карток.

Середній cycle time обчислюється за формулою:

`Середній cycle time = сума cycle time завершених карток / кількість завершених карток`

Незавершені картки не включаються до розрахунку.

**Колонка, у якій картки чекали найдовше, і чому саме там:**

Визначається після двотижневого спостереження.

Для цього використовую історію переміщень карток у GitHub Projects і фактичні спостереження за накопиченням роботи в Ready, In progress та Review.

Потрібно назвати конкретну колонку й пояснити причину очікування: відсутність готових матеріалів, блокування зовнішньою залежністю, перевантаження перевірки або іншу підтверджену причину.

**Висновок першого виміру:**

Заповнюється після завершення періоду спостереження 2026-11-19.

У висновку потрібно зазначити фактичну кількість завершених карток, діапазон cycle time та головне вузьке місце процесу.

## 7. Рішення ретроспективи з ЛР3

**Як воно звучить:**

Після симуляції Scrum-спринта в ЛР3 було визначено проблему: команда включила до спринта історію S-09, яка залежала від зовнішньої системи розкладу занять, але не перевірила готовність цієї залежності.

Через затримку відповіді від власника зовнішньої системи історія S-09 залишилася незавершеною, а початкова ціль спринта не була досягнута.

На ретроспективі ухвалено рішення:

**Перед плануванням кожного спринта перевіряти готовність зовнішніх залежностей.**

Для кожної інтеграції необхідно:

1. Визначити відповідального за зовнішню систему.
2. Підтвердити доступ до тестового середовища.
3. Зафіксувати дату та канал отримання відповіді.
4. Перевірити доступність необхідної документації.
5. Не брати історію до спринту, якщо критичні залежності не готові.

**Що з ним сталося на дошці за два тижні:**

Для виконання цього рішення створено картку F-001:

«Ввести перевірку готовності зовнішніх залежностей перед плануванням».

Картку створено 2026-11-06 і визначено першою для виконання.

Очікуваний результат — чекліст перевірки інтеграцій та його застосування до історії S-09 із ЛР3.

Фактичну дату завершення, результат перевірки та посилання на готовий чекліст буде додано після виконання F-001.

Під час підсумкового аналізу 2026-11-19 потрібно визначити, чи виконано рішення ретроспективи, чи залишилося воно лише запланованим завданням.
