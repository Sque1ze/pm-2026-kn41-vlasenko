# Definition of Done (DoD) — сервіс бронювання аудиторій

**Проєкт:** V06, сервіс бронювання аудиторій і обладнання з погодженням заявок.  
**Підхід:** один автор виконує більшість робіт; іншу людину як обов’язкового рев'юера не передбачається.  
**Статус:** запропоновані критерії для реальних інкрементів; їх виконання треба підтверджувати окремо.

## Єдині умови завершеності для кожної історії

1. **Acceptance criteria виконано.** Для кожного критерію історії з `lr06_backlog/backlog.csv` наведено результат перевірки та посилання на доказ (тест, скріншот або протокол). Відповідь: так/ні.
2. **Позитивний і негативний сценарії перевірено.** Є щонайменше один успішний і один помилковий/граничний сценарій з фактичним результатом; якщо для історії негативний сценарій непридатний, причина записана. Відповідь: так/ні.
3. **Не зламано пов'язані функції.** Повторено контрольні перевірки зміненого процесу (вхід, права, каталог, бронювання або статус) і задокументовано результат. Відповідь: так/ні.
4. **Зроблено повторну самоперевірку.** Після завершення роботи автор проходить чекліст і переглядає зміни повторно в іншу робочу сесію; критичні зауваження з цього перегляду усунуті. Відповідь: так/ні.
5. **Немає невирішених критичних або високих дефектів.** Перелік відомих дефектів переглянуто і для історії не залишено незакритих дефектів рівня critical/high. Відповідь: так/ні.
6. **Артефакти синхронізовані.** Зміни збережені в репозиторії, посилання на результат є у трекері, а опис історії/документація оновлені там, де змінюється поведінка. Відповідь: так/ні.
7. **Готово до показу на Sprint Review.** Є короткий відтворюваний сценарій демонстрації та відома версія/коміт артефакта. Відповідь: так/ні.

8. **Перевірено безпеку персональних даних.** Для історій, що обробляють персональні дані, є доказ відповідності обов’язковим вимогам академії (академічний вхід без локальних паролів, протокол переглядів та доступна сторінка строків зберігання); для історій без доступу до персональних даних є обґрунтована відмітка «не застосовується». Поки офіційні вимоги не реалізовані, такі історії не можна вважати готовими до виробничого запуску. Відповідь: так/ні.

**Правило:** Story Points нараховуються лише тоді, коли виконані всі вісім умов. Часткові результати не зараховуються як повністю завершена вихідна історія.

## Чого DoD свідомо не вимагає

- Обов’язкового code review другою людиною, бо для навчального індивідуального проєкту другий виконавець не гарантований; заміна — повторна самоперевірка за чеклістом.
- Формального автоматичного CI для кожної документальної правки. Там, де є код, використовуються доступні тести та статичний аналіз; для CSV обов’язковий валідатор курсу.
- Відсутності будь-якого низькопріоритетного дефекту: такі питання фіксуються як зауваження або борг із рішенням, але не приховуються.

## Як це працює на практиці

За доступними матеріалами **жодна історія S-01–S-15 поки не має перевіреного підтвердження проходження всіх восьми умов у двох реальних спринтах**. Це не означає, що робіт не було: це означає, що у `sprints.md` ще не зафіксовано докази готових інкрементів. Тому кількість **підтверджено закритих за цим DoD історій — 0** (стан документа, не остаточний результат спринтів).

Після кожного Sprint Review треба зазначити ключі історій, які пройшли DoD, і скоригувати `lr03_sprint_simulation/sprints.md` та `lr09_forecast/velocity.csv` за фактом.

**Відхилення від DoD:** може письмово погодити керівник навчальної частини як представник замовника після опису ризику, але така історія не вважається Done для підрахунку velocity, доки невиконану умову не усунено.

**Відмінність від acceptance criteria:** критерії приймання описують функцію конкретної історії; наведений DoD — спільний стандарт якості для всіх історій.
